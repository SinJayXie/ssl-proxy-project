# UDP 支持方案研究：代理 or 直连

> 状态：方案草案（未实施）
> 适用版本：gui 2.3.2 / svr 1.2.0 之后
> 关联文档：[ARCHITECTURE.md](../crates/svr/docs/ARCHITECTURE.md)

---

## 1. 背景

当前 SSL Proxy 只处理 TCP：

```text
应用 ──▶ 127.0.0.1:1080（SOCKS5 / HTTP）
          ├─ 规则匹配 ──▶ 直连（TCP）
          └─ TLS 隧道（私有协议帧）──▶ svr ──▶ 目标（TCP）
```

SOCKS5 仅实现了 CONNECT（`cmd=0x01`）。DNS 查询、QUIC / HTTP-3、语音视频（WebRTC）、游戏等 UDP 流量当前的表现是：应用通过 TCP 代理拿不到 UDP 能力，通常回退到 TCP 或直连失败。

**核心问题**：客户端收到 UDP 请求后，直连还是经服务端转发？如果转发，走什么通道？

---

## 2. 需求与约束

| # | 需求 / 约束 | 说明 |
| - | ----------- | ---- |
| R1 | 不破坏伪装性 | 项目核心卖点是"单 TLS 端口 + 伪装站点"。新增通道不能引入明显的代理特征 |
| R2 | 路由一致 | UDP 必须复用现有 HOST / GEO / `directs` 规则体系 |
| R3 | 低延迟可选 | 游戏、语音对"UDP over TCP"的队头阻塞敏感，但不能为它牺牲 R1 |
| R4 | 改动收敛 | 服务端保持单端口理念，配置项增量最小 |
| R5 | 客户端接入方式 | SOCKS5 UDP ASSOCIATE（RFC 1928，主流应用原生支持） |

---

## 3. 候选方案对比

### 方案 A：UDP 全部直连（不建 UDP 代理通道）

客户端实现 SOCKS5 UDP ASSOCIATE，本地起 UDP socket，按规则分流，命中代理的 UDP 流量也直接从本机发出。

- **优点**：实现最简单，零服务端改动，延迟最优。
- **缺点**：代理的"翻墙"能力对 UDP 完全失效——被墙的 UDP（如部分 QUIC、STUN）直连仍然不通；客户端 IP 直接暴露给目标。
- **结论**：只适合作为"规则未命中 / 用户显式选择"的**回退路径**，不能作为唯一方案。本质上等价于现有 `directs` 机制的 UDP 版。

### 方案 B：UDP over TLS（复用现有 TCP 隧道）

UDP 数据报封装成私有协议帧，在现有 TLS 隧道内传输；服务端解包后用 UDP socket 转发，并维护 NAT 映射表。

```text
应用 ──UDP──▶ SOCKS5 UDP ASSOCIATE ──┐
                                     │ 封帧（新增 UDP 帧类型）
              现有 TLS 隧道（TCP）────┘
                                     │
svr：解帧 ──▶ UDP socket 池（四元组 NAT 表）──▶ 目标
```

- **优点**：
  - 完全复用现有 TLS 伪装、HMAC 认证、mux 复用，**服务端端口不变**，伪装性最好（R1/R4 全满足）；
  - 可靠有序的 TCP 承载，弱网下不丢包（对 DNS 类"必须成功"的查询反而友好）；
  - 实现量最小：客户端隧道层加一种帧类型，服务端加一个 UDP relay 模块。
- **缺点**：
  - TCP 队头阻塞 + 重传，UDP 低延迟语义受损（RTT 约 +1 RTT，丢包时放大）；
  - 服务器侧 UDP NAT 会话需要超时回收（常规 30s~60s，TCP keepalive 帧维持）。
- **结论**：**推荐作为第一期方案**。覆盖 DNS、QUIC 兜底、大部分代理需求，风险最低。

### 方案 C：独立 UDP 通道（原生 UDP 转发）

服务端另开一个 UDP 端口，客户端与服务端之间用 DTLS / QUIC / 裸 UDP+HMAC 传输，服务端 relay。

- **优点**：保留 UDP 无连接低延迟语义，游戏/语音体验最好。
- **缺点**：
  - **多开一个端口，破坏单端口伪装**（一个 IP 上"HTTPS 站点 + 常驻 UDP 高位端口"是可识别特征）；
  - 需要自建会话/加密/重放防护（裸 UDP + HMAC 要自己处理序列号防重放、MTU 探测、分片），工作量约为 B 的 3~4 倍；
  - UDP 被运营商 QoS / 阻断的概率高于 TCP（恰恰是本项目要解决的场景）。
- **变体 C'**：用 QUIC Datagram（quinn crate），伪装成 HTTP/3 流量，防重放/加密免费获得。但仍是独立端口 + 新协议栈，且"服务器同时是 HTTPS 站点和 QUIC 服务"的指纹需要实测。
- **结论**：作为**第二期可选增强**，仅在方案 B 实测延迟不满足需求时再做。

### 方案 D：透明代理 / TUN 虚拟网卡

客户端装 TUN 网卡接管系统全部 UDP。

- **结论**：超出当前产品形态（本地代理端口模式），需要管理员权限、驱动签名，改动面过大。**不采用**，仅在产品形态升级时再评估。

### 对比总表

| 维度 | A 直连 | B UDP over TLS | C 独立 UDP 通道 | D TUN |
| ---- | ------ | -------------- | --------------- | ----- |
| 伪装性 | —（不走代理） | ★★★ 复用现有 | ★★ 新增端口 | ★★★ |
| 延迟 | ★★★ | ★★ 队头阻塞 | ★★★ | ★★★ |
| 抗封锁 UDP | ✗ | ✓（走 TCP/TLS） | 部分（UDP 易被 QoS） | 取决路由 |
| 服务端改动 | 无 | 小（+1 模块） | 大（新协议栈） | — |
| 实现周期 | 短 | 中 | 长 | 很长 |
| 覆盖场景 | 规则命中直连 | DNS/QUIC/一般 UDP | +游戏/实时音视频 | 全部 |

## 4. 推荐方案：A + B 分阶段落地

```text
                    ┌─ 规则命中直连 ──▶ 本机直接 UDP 出口
应用 UDP ──▶ 本地   │
分流器              └─ 规则命中代理 ──▶ UDP 封帧 ──▶ 现有 TLS 隧道 ──▶ svr UDP relay
```

### 4.1 客户端（crates/gui）

1. **SOCKS5 UDP ASSOCIATE**
   - `handle_socks5_client`（`core/proxy/socks5.rs`）支持 `cmd=0x03`：回复 BND.ADDR 指向本地 UDP 中继端口；
   - 新增 UDP 中继监听：解析 SOCKS5 UDP 报文头（`RSV/FRAG/ATYP/DST.ADDR/DST.PORT` + payload），FRAG≠0 的分片暂不支持（主流应用很少用），直接丢弃；
   - 每个目标五元组对应一条路由决策（复用 HOST / GEO / `directs` 逻辑），直连或进隧道。
2. **隧道层新增 UDP 帧类型**
   - 在 `core/proxy/framing.rs` / `mux.rs` 增加帧类型 `UDP_DATA` / `UDP_CLOSE`；
   - 帧负载：`流ID(会话标识) + ATYP + 地址 + 端口 + 报文长度 + payload`，同一"UDP 会话"（客户端 socket → 目标）复用同一流 ID，便于服务端 NAT 映射与统计；
   - mux 关闭时 UDP 会话随隧道一起失效（接受此语义，客户端自动重建）。
3. **配置**（`setting.yaml`）
   - `udpMode: "off" | "direct" | "proxy"`，默认 `off`（不监听 UDP ASSOCIATE，行为与旧版一致）；`proxy` 即上述 A+B 路由。

### 4.2 服务端（crates/svr）

1. **新增 `services/udp_relay_service.rs`**
   - 解析 `UDP_DATA` 帧 → 查 NAT 表（`DashMap<流ID, UdpSocket>`）→ 未命中则 `bind(0.0.0.0:0)` 新建 socket 并 spawn 转发任务；
   - 回包封装为 `UDP_DATA` 帧写回 TLS 隧道；
   - 会话空闲超时（默认 60s，可配 `udp.timeout-secs`）回收 socket；
   - 每连接报文速率限制，复用 `rate_limit` 思路防滥用。
2. **协议兼容性**
   - 新帧类型对旧服务端是未知帧：客户端应先探测（服务端版本/能力字段，或在 mux 握手响应中带能力位），服务端不支持时客户端自动降级为 `direct` 模式，避免出现"配置了代理但 UDP 全挂"。

### 4.3 统计与 UI

- 连接列表新增 UDP 会话条目（协议列显示 `UDP`，目标地址、上下行流量）；
- `stats.json` 增加 UDP 流量计数；
- 设置页新增「UDP 转发」开关（off / 直连 / 代理）。

### 4.4 边界与不做的事

- 不支持 SOCKS5 UDP 分片（FRAG）；
- 不做全文 UDP over QUIC（方案 C）一期实现；
- HTTP 代理（CONNECT）本身无 UDP 语义，不涉及；
- DNS：建议仍走现有 TCP DNS / 直连解析路径，不必强行走 UDP 代理（现有 `core/dns.rs` 已可用 trust-dns 的 TCP 模式兜底）。

## 5. 风险与开放问题

| 风险 | 影响 | 缓解 |
| ---- | ---- | ---- |
| TCP 队头阻塞导致 QUIC 类应用体感差 | 中 | QUIC 本身在 TCP 上会退化为 HTTP/2，实际损失有限；二期上方案 C |
| 服务端 UDP 被用于打流量（放大攻击跳板） | 高 | 出站目标限速 + 禁止回环/内网地址段（防 SSRF）+ 空闲回收 |
| 旧服务端收到未知帧 | 兼容 | 能力探测 + 客户端自动降级 direct |
| 长连接 NAT 被中间设备断开 | 低 | mux keepalive 已有；UDP 会话随隧道重建 |

**开放问题**（实现前需确认）：

1. mux 模式与非 mux 模式下 UDP 会话的生命周期语义（建议：非 mux 时每条 TLS 连接只承载一个 UDP 会话，实现最简）；
2. 服务端 UDP 出口是否需要绑定特定网卡/地址（复用现有绑定配置）；
3. UDP 会话是否纳入 GEO 直连地区回退的统计口径。

---

## 6. 实施拆分建议

1. **P0 客户端直连**：SOCKS5 UDP ASSOCIATE + 规则分流直连（方案 A），独立可发布；
2. **P1 隧道转发**：UDP 帧类型 + 服务端 UDP relay + 能力探测降级（方案 B）；
3. **P2 打磨**：UI/统计/限速配置 + 弱网联调；
4. **P3（可选）**：评估方案 C'（QUIC Datagram 通道）。

P0 与 P1 可分开发版，P0 本身就能解决"应用因无 UDP 而异常"的大部分反馈。
